## ⚠️ Read this before committing compute: the RNAseq evidence is weak

Phase 4's premise is that BRAKER3 adds **ecotype-specific genes that Liftoff cannot transfer**,
using RNAseq + protein evidence. The RNAseq named in the plan is `PRJNA316738`. Parsed from
[`data/SraRunTable.csv`](../data/SraRunTable.csv):

| Property | Value |
|---|---|
| Runs | 72 (18 per ecotype × parasitized/non) |
| Read length | **36 bp** |
| Layout | **SINGLE-end** |
| Instrument | Illumina Genome Analyzer IIx (2016) |
| Tissue | **Liver only** |
| Total | 17.8 Gbp (13.4 GB download) |

Two problems, both material:

1. **36 bp single-end reads are near-useless for splice-junction discovery.** A spliced aligner
   needs a meaningful anchor on both sides of a junction; at 36 bp almost no read spans an intron
   with enough flank to call it confidently. RNAseq's job in BRAKER3 is precisely to supply intron
   hints. These reads will supply very few.
2. **Liver-only means a tissue-restricted transcriptome.** Genes not expressed in adult liver get
   no RNA evidence at all — and there is no reason to think ecotype-divergent genes (lipid/buoyancy,
   depth adaptation) are all liver-expressed.

**Recommendation: make protein evidence the primary arm.** Run BRAKER in **protein-mode**
(OrthoDB Actinopterygii v11 + SaNama RefSeq proteins) as the deliverable, and run the RNAseq arm
alongside it as a comparison rather than the backbone. Protein homology does not depend on read
length and is not tissue-restricted. The scripts below implement both arms; `ARM=protein` is the
default.

**The real fix, if Phase 4's conclusions are to carry weight,** is modern RNAseq — paired-end
≥100 bp, multiple tissues, both ecotypes. That is a sequencing decision, not a compute decision, and
it is worth making before anyone leans hard on "ecotype-specific gene" counts from this phase.

**Why purged, and why it matters:** Phases 2 and 3 ran on these exact purged assemblies
([`23.4-reciprocal-pav.py`](23.4-reciprocal-pav.py), [`23.8-native-meth-pipeline.py`](23.8-native-meth-pipeline.py)).
Annotating the unpurged primaries instead would put Phase-4 gene models on a coordinate system that
does not match the reciprocal-PAV and native-DMG results, and the whole point of Phase 4 is to feed
the Phase-5 "≥2 independent lines of evidence" integration. Purged also drops ~1.2 Gb of retained
haplotig sequence per assembly, which would otherwise generate duplicate gene models that look like
ecotype-specific genes and are not.

The Liftoff GFF3s already exist for both purged assemblies, so the TSEBRA merge input is ready.

## One de novo repeat library, not two

RepeatModeler2 is the single most expensive step (days to weeks on a 2.6 Gb salmonid). The plan as
written implies one run per assembly.

**Lean and siscowet are the same species** (*S. namaycush*). Their repeat content is effectively
identical. Build **one** de novo library on the lean assembly, then RepeatMask both assemblies with
`lean_denovo_library + Dfam Salmoniformes`. This halves the dominant cost with no meaningful loss —
and if anything improves consistency, since both assemblies then get masked against identical
library, removing a confound where differential masking creates apparent gene-model differences.

## Klone layout

```
/gscratch/scrubbed/$USER/lake-trout-phase4/      # working scratch (21-day purge!)
  00_inputs/      assemblies, proteins, orthodb
  01_repeats/     RepeatModeler2 + RepeatMasker
  02_rnaseq/      SRA fastqs, HISAT2 index, BAMs      (secondary arm only)
  03_braker/      {lean,siscowet}/ per arm
  04_merge/       TSEBRA
  05_specific/    reciprocal ecotype-specific screen
  06_function/    eggNOG-mapper, InterProScan, BUSCO
/gscratch/srlab/$USER/lake-trout-phase4/final/   # keep: survives the scrubbed purge
```

Anything you intend to keep **must** move to `/gscratch/srlab` before the scrubbed window expires.
A multi-week RepeatModeler run plus a scrubbed purge is a recoverable disaster, but an annoying one.

Software follows the `/srlab/programs/miniforge3-24.7.1-0/envs/...` convention from
[`13.1-hifiasm-genome-assembly-lean.Rmd`](13.1-hifiasm-genome-assembly-lean.Rmd) and
[`20.1-liftoff-annotation.Rmd`](20.1-liftoff-annotation.Rmd). **BRAKER3 is the exception — use the
Apptainer container**, not conda: it bundles GeneMark-ETP, AUGUSTUS, ProtHint and DIAMOND at
compatible versions, which is painful to reproduce by hand.

```bash
apptainer build braker3.sif docker://teambraker/braker3:latest
```

Two container gotchas that cost a day each if missed:
- `AUGUSTUS_CONFIG_PATH` must point at a **writable** copy. Copy it out of the container first.
- GeneMark needs a valid licence key at `~/.gm_key`. Check its expiry *before* queueing a 3-day job.

## Steps, resources, walltime

Resource numbers assume a standard Klone compute node. **Verify against `hyakalloc` before
submitting** — partition names, core counts and the lab's allocation ceiling change.

| # | Step | Script | Cores | RAM | Walltime | Notes |
|---|---|---|---|---|---|---|
| 0 | Stage inputs, md5 freeze | `00-stage.sbatch` | 4 | 16G | 2h | rsync from local box |
| 1 | RepeatModeler2 (lean only) | `01-repeatmodeler.sbatch` | 32 | 120G | **7d ×N** | checkpointed, see below |
| 2 | RepeatMasker ×2 | `02-repeatmasker.sbatch` | 32 | 64G | 1–2d | array job, 2 tasks |
| 3 | RNAseq fetch + align | `03-rnaseq.sbatch` | 16 | 32G | 8h | secondary arm only |
| 4 | BRAKER ×2 | `04-braker.sbatch` | 32 | 120G | 2–4d | array job, 2 tasks |
| 5 | TSEBRA merge w/ Liftoff | `05-tsebra.sbatch` | 4 | 32G | 2h | |
| 6 | Reciprocal specificity screen | `06-specific.sbatch` | 16 | 64G | 6h | miniprot, see below |
| 7 | eggNOG + InterProScan + BUSCO | `07-function.sbatch` | 32 | 64G | 1d | |

### Step 1 is the one that needs care

RepeatModeler2 on 2.58 Gb will very likely exceed any single walltime window. Build recovery in
from the start:

```bash
# first submission
RepeatModeler -database lean -threads 32 -LTRStruct
# resubmission after timeout — points at the round directory left behind
RepeatModeler -database lean -threads 32 -LTRStruct -recoverDir RM_<pid>.<date>
```

`01-repeatmodeler.sbatch` auto-detects the newest `RM_*` directory and appends `-recoverDir`, so the
same script can simply be resubmitted until it completes. If you run on the preemptible `ckpt`
partition to avoid burning allocation, this is not optional — it is the only thing that makes the
job survivable.

### Step 6 is a correctness step, not a formality

A BRAKER model present in lean and absent from siscowet's annotation is **not** evidence of an
ecotype-specific gene. It is equally consistent with prediction failure on the other assembly. The
screen maps each candidate's protein back to the *other* ecotype's genome with `miniprot` and keeps
only candidates with no credible genomic locus there — i.e. genomic absence, not annotation absence.
Candidates that survive should then be cross-referenced against the Phase-2 reciprocal-PAV calls
(`analyses/23-reciprocal-pav/`); agreement between two independent methods is exactly the ≥2-lines
standard Phase 5 is meant to apply.

Expect this screen to discard a large fraction of naive "ecotype-specific" calls. That is the screen
working, not failing.

## Decision points before launching anything

1. **Evidence arm.** Protein-primary (recommended) vs RNAseq-primary vs both. Drives steps 3–4.
2. **New RNAseq?** If modern paired-end multi-tissue RNAseq is plausible on any timescale, it may be
   worth deferring BRAKER until it exists, rather than annotating twice.
3. **Partition.** Allocated (predictable, burns the lab's hours) vs `ckpt` (free, preemptible,
   mandatory checkpointing). RepeatModeler on `ckpt` is viable *only* with step 1's recovery logic.
4. **GeneMark key validity** — check `~/.gm_key` expiry now, not after a 3-day queue wait.
5. **Is Phase 4 worth it at all?** Phases 1–3 are the scientific core and are complete; the plan
   itself says Phase 4 can be deferred. Given the RNAseq limitation above, a defensible alternative
   is to **skip to Phase 5** with Liftoff-only annotation and state the ecotype-specific-gene
   question as explicitly open pending better transcriptome data.
